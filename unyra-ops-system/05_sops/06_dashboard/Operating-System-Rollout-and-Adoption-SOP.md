# Operating System Rollout and Adoption SOP

This SOP defines how UNYRA moves the operating system from premium structure into repeatable operating habit. Adoption is not measured by how polished the repository looks; it is measured by whether the right control layer opens before decisions, live gates, payment movement, shipment release, customer communication, supplier dependence, and founder approvals.

## SOP Control Posture

| SOP Control | Current Standard | Founder Use |
| --- | --- | --- |
| Status | ACTIVE SOP | Use as the operating standard for system rollout, habit formation, adoption checks, and maturity gates. |
| Purpose | Move UNYRA from setup into sustained use quality across CRM, operations, compliance, dashboards, SOPs, archive, and working-file custody. | Keeps the founder focused on behavior change, not just document polish. |
| Source rule | Review adoption board, control routing matrix, control integrity review, executable-check board, owner accountability, task tracker, funding review, release review, and linked functional dashboards before declaring maturity. | Prevents the system from being called adopted while live gates still rely on memory. |
| Decision rule | Adoption exists only when teams use the correct control layer before decisions, movement changes, live gates, or founder approvals. | Blocks after-the-fact documentation from masquerading as operating discipline. |
| Template protection | Keep live working copies outside protected template folders and preserve approved template masters while adoption practices mature. | Protects `01_templates/` and approved standards during rollout pressure. |

## Adoption Principle

| Principle | Required Adoption Behavior | Founder Reading |
| --- | --- | --- |
| Structure is not enough | Beautiful structure does not equal adoption unless the correct layer is used before decisions. | A polished room is only useful when it changes behavior under pressure. |
| Operating habit is the maturity test | Naming, routing, refresh discipline, owner follow-through, and closeout behavior become normal. | Adoption should reduce founder rescue rather than document it. |
| Live gates require executable proof | Trust-linked release, payment, shipment, or communication logic opens the executable-check layer before movement widens. | Same-day pressure is the real adoption exam. |
| Source discipline comes before polish | Dashboards are trusted only after linked source records are current and decision-ready. | Dashboard confidence must stay downstream of proof. |
| Closeout quality proves maturity | Shipment review, profitability, CAPA, archive, and lesson capture close as strongly as the system opens. | Adoption is incomplete if work opens formally but closes from memory. |

## Rollout Phase Model

| Phase | Founder Standard | Pass Signal | Hold Signal |
| --- | --- | --- | --- |
| Structure setup | Folders, portals, templates, rooms, dashboards, and preview surfaces exist with protected masters preserved. | Navigation is clear and protected templates stay untouched. | Teams still ask where a matter belongs. |
| Guided use | Founder or operating owner routes live issues into the correct layer before action. | Teams can follow the control route with founder prompting. | Decisions still begin in chat or memory. |
| Habit formation | Owners open source rooms, dashboards, tasks, release gates, and executable checks without founder chase. | Control usage appears before movement, payment, or communication. | Records are refreshed only after the founder asks. |
| Stress test | Same-day release, funding, supplier response, claim, or customer pressure uses the correct gate under urgency. | Executable-check and control-integrity records stay current while pressure is live. | Urgency creates shortcuts or fragmented stop rules. |
| Maturity | The system reduces founder rescue, preserves proof, and closes work with archive-ready evidence. | Owners, deadlines, source records, dashboards, and closeout paths agree without founder reconstruction. | Founder still acts as missing owner, memory, or evidence router. |

## Warning Signs

| Warning Sign | Why It Matters | Required Founder Response |
| --- | --- | --- |
| Chat-first decisions | Teams make decisions before opening the right review layer. | Route the matter through control routing before action continues. |
| Template contamination | Working files appear in `01_templates/`. | Move live work into owned rooms and preserve protected masters. |
| Repeated founder exceptions | One matter accumulates exceptions without exception governance. | Open exception governance and owner accountability before further movement. |
| Stale source records | A dashboard looks polished while linked source rooms are stale. | Refresh source rooms and run control integrity before decision. |
| Executable-check bypass | Release, payment, shipment, or communication widens while the executable-check layer is stale, missing, or only in chat. | Stop widening and require executable-check routing. |
| Containment without closure | Cases are contained but not closed through profitability, CAPA, shipment review, or archive logic. | Keep matter active until closeout proof is route-backed. |
| Founder rescue becomes routine | The founder keeps supplying owner memory, deadlines, or proof location. | Move the pattern into owner accountability and adoption review. |

## Live-Gate Adoption Standard

| Gate Type | Required Before Movement Widens | Adoption Failure |
| --- | --- | --- |
| Release gate | Release record, executable-check board, scenario response, risk register, and source room carry the same current answer. | Broker handoff or movement widens because packet exists. |
| Funding gate | Funding release, cash outlook, release gate, packet proof, and executable-check record agree. | Supplier payment moves because urgency or relationship pressure rises. |
| Customer communication gate | Communication control, response SLA, trust posture, and counterparty room agree before outward language leaves. | Message is sent from chat or memory without release controls. |
| Supplier response gate | Supplier packet, response escalation, supplier performance, and supply resilience agree. | Supplier confirmation compresses the decision window and the system catches up later. |
| Archive gate | Shipment review, document control, task closure, executable-check proof, and archive closeout agree. | Matter is treated as finished before retrieval proof exists. |

## Monthly Adoption Check

| Monthly Check Step | Required Action | Maturity Standard |
| --- | --- | --- |
| Refresh linked controls | Refresh founder dashboard, control routing matrix, control integrity review, owner accountability, executable-check board, task tracker, funding review, release review, and linked functional dashboards first. | Adoption is judged from current evidence, not static structure. |
| Open adoption board | Open `06_dashboard/35_system-adoption/Operating-System-Adoption-and-Readiness-Board.md`. | The board becomes the monthly maturity scorecard. |
| Judge use quality | Decide whether the system reduces founder rescue, improves closure quality, keeps work inside right layers, and opens executable checks before live movement widens. | Usage quality matters more than folder count. |
| Apply maturity gate | Do not call the operating system mature until disciplined use quality holds without founder forcing. | Founder is no longer the missing executable-check owner at live gates. |
| Record next adoption action | Put the next gap into owner accountability, adoption board, or weekly review. | Adoption issues become managed work, not private frustration. |

## End-of-Cycle Closeout

| Closeout Test | Required Evidence | Adoption Reading |
| --- | --- | --- |
| Source rooms are current | CRM, operations, compliance, dashboard, SOP, and archive source records are updated before founder calls. | The system is being used before decisions. |
| Live gates are executable | Release, payment, shipment, trust override, and communication gates have owner, cutoff, evidence, and closure route. | Same-day pressure is governed by the system. |
| Owners are visible | Every active adoption gap has owner, deadline, route, and escalation standard. | Founder rescue is declining. |
| Working files are governed | Settled files leave temporary custody and protected templates remain clean. | Folder discipline is holding under pressure. |
| Lessons are retained | Shipment review, profitability, CAPA, and archive routes preserve what happened. | Closure quality matches opening rigor. |
